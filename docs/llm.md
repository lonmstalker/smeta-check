# Нейросеть: настройка, смена модели, данные пользователей

Пошаговая инструкция для оператора. Что и почему устроено именно так —
план `docs/plans/2026-07-llm-integration.md`, разведка про данные —
`docs/llm-data.md`.

## Включить

Три переменные (читаются только в `core/config.rs`):

| Переменная | Что это | По умолчанию |
|---|---|---|
| `LLM_API_KEY` | ключ провайдера. Пусто — нейросеть выключена целиком: фото не принимаются, Excel работает как раньше | пусто |
| `LLM_BASE_URL` | база OpenAI-совместимого API, без `/chat/completions` | `https://openrouter.ai/api/v1` |
| `LLM_MODEL` | идентификатор модели у провайдера | `google/gemini-3.1-flash-lite` |

Ключ живёт только в `.env` (dev) и `.env.prod` (прод) — оба в `.gitignore`.
В код, тесты, логи и журнал ключ не попадает: в логах он невозможен, потому
что тип `Secret` печатает звёздочки, а тесты ходят в фейкового провайдера.

## Запретить обучение на наших данных (обязательно до прода)

Кодом это не делается — так устроены все провайдеры. Настройка в аккаунте:

- **OpenRouter**: в настройках аккаунта выключить `data collection` (запрет
  на хранение и обучение) и включить маршрутизацию только через
  ZDR-эндпоинты. Проверить, что выбранная модель есть в списке ZDR:
  `curl -s https://openrouter.ai/api/v1/endpoints/zdr | grep <модель>`.
- **Любой другой провайдер**: найти в его условиях пункт про обучение на
  данных API и включить запрет. Нет такого пункта — провайдер не годится
  для пользовательских фото.

Именно эта настройка делает честной строку у формы загрузки («без
сохранения и без обучения на ваших данных»). Сменил провайдера или модель —
проверь запрет заново, до первого пользовательского фото.

## Фото пользователей и российский провайдер

Фото сметы может содержать персональные данные (ФИО, телефон, адрес). Их
передача за границу — отдельное уведомление РКН с риском отказа, поэтому
прод-дефолт для пользовательских фото — российский провайдер с
OpenAI-совместимым API (Yandex AI Studio: серверы в РФ; GigaChat — через
адаптер gpt2giga). OpenRouter остаётся для разработки и задач без ПДн.

Переезд — это `LLM_BASE_URL` + `LLM_API_KEY` + `LLM_MODEL` и перезапуск:
кода касаться не нужно. После переезда обязателен замер (ниже) — качество
у моделей разное.

## Сменил модель или провайдера — перемеряй

Планка одна и та же: на читаемом кадре ≥90% строк распознано, строк с
неверным числом ≤1%, выдуманных чисел — ноль.

```
node scripts/llm-probe.mjs --models <id> --limit 1   # сначала дёшево
node scripts/llm-probe.mjs                            # потом весь корпус
```

Корпус и ключи — локальные (`fixtures-local/`, `.env.probe`), в git не идут;
состав описан в `fixtures-local/README.md`. Кандидаты перечислены списком в
начале скрипта — новую модель добавлять туда.

**Пересчитай потолок.** Дневной потолок токенов — константа
`DAILY_TOKENS_CAP` в `server/src/core/llm.rs` (2 млн токенов в сутки по
UTC). Сколько это фото — зависит от модели: замер печатает «токенов/фото»,
дели одно на другое. При замере F0 выходило около тысячи фото в день.
Потолок выбран — фото не пропадают: смета остаётся в очереди и разбирается
после полуночи UTC.

## Что смотреть, когда «фото не разбираются»

- `llm_calls_total{result}` — `ok`, `capped` (выбран потолок), `http_error`
  (провайдер ответил ошибкой: чаще всего неверный ключ или его лимит),
  `timeout`, `transport` (не дошли до провайдера).
- `llm_tokens_total{kind}` — сколько токенов ушло за prompt и completion.
- В логах — `провайдер нейросети ответил ошибкой` со статусом и началом
  тела ответа. Ключ в логах не появляется никогда.
- Таблица `llm_calls` — только счётчики (модель, токены, время). Ни фото,
  ни ответов модели там нет и не будет: нечему утекать. Записи старше 30
  дней убирает фоновая уборка.

## Прод-пререквизиты (без них фото не включаем)

1. Работающий SMTP: фото принимаются только у пользователей с
   подтверждённой почтой, а без писем почту не подтвердить.
2. Опубликованная политика конфиденциальности с разделом про
   ИИ-провайдера и строка согласия у формы загрузки.
3. Разовая консультация юриста про трансграничную передачу и уведомление
   РКН — либо переезд на российского провайдера (см. выше).
