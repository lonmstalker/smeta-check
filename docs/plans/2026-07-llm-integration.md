# План: интеграция с LLM — распознавание смет с фото и PDF

Статус: ЧЕРНОВИК — два круга валидации (2026-07-31): пять ракурсов,
перекройка на фото/PDF по решению человека, затем повторные
pre-mortem и сверка с кодом; их замечания вшиты ниже. Ключевые
вопросы открыты, реализацию не начинать.

Цель волны: научить сервис звать LLM через любой OpenAI-compatible
API за предохранителями из product.md и подключить первого
настоящего потребителя — распознавание сметы, загруженной
фотографией (PDF — вторым шагом). Провайдер — любой
OpenAI-compatible; для пользовательских фото приоритет —
российский (трансграничная передача ПДн, см. «Закрыто разведкой»),
OpenRouter — для разработки и данных без ПДн; смена — правкой
конфига. Основание — product.md: «LLM —
для фото/кривых PDF», «смету чаще всего фотографируют с телефона» —
а сегодня сервис фото вообще не принимает.

## Решения человека (2026-07-31, закрыты)

- **Первый потребитель — фото/PDF**; Excel остаётся алгоритмике.
- **Фильтр data policy обязателен**: провайдер/модель не обучаются
  на наших данных.
- **Дневной потолок — 2 млн токенов/день, константой** (после
  замера F0 пересчитывается в «фото/день»; если выйдет меньше ~100
  фото — вернуться к человеку с числом).

## Вопросы (открытые)

1. **PDF — каким способом**: (а) разбор силами провайдера
   (привязка к нему) или (б) растеризация у нас (нативная
   зависимость). Решаем в F6 по фактам F0/F4.

## Закрыто разведкой (2026-07-31, подробности — `docs/llm-data.md`)

- **Согласие**: строка у формы («фото обработает нейросеть; ПДн не
  нужны — можете замазать»; непредзаполненная) + гарантия
  «пользователь вправе загружать документ» в правилах + раздел про
  ИИ-провайдера в политике + ZDR/запрет обучения у провайдера.
  Юрист (трансграничка, РКН) и публикация политики — пререквизиты
  ПРОДА, не старта кода. Покрывает и будущие «сметы пользователей
  для ценовой базы».
- **Трансграничная передача**: «ПДн за границу» — не запрет, а
  уведомление РКН с риском отказа (США вне перечня адекватных).
  Решение: прод-дефолт для пользовательских фото — российский
  провайдер (Yandex AI Studio, OpenAI-совместимый API официальный,
  серверы в РФ; GigaChat — через адаптер gpt2giga), пока юрист не
  согласует иное; OpenRouter — для разработки и не-ПДн задач.
  Строка согласия зависит от пути («сервис за пределами РФ» —
  только для зарубежного).
- **Корпус фикстур F0** (телефонных фото смет в открытом доступе
  почти нет; чужих PDF/скриншотов — десятки, ссылки в
  `llm-data.md`): распечатки ЧУЖИХ реальных PDF-смет, снятые
  телефоном с живыми артефактами (числа известны из PDF — готовый
  ground truth; только локально, в git не идут); скриншоты смет
  (пользователи шлют и их); класс «рукопись» — 20–50 НАСТОЯЩИХ
  рукописных товарных чеков со стройрынков (соседний подкласс, тот
  же визуальный тип; легко находятся) + 5–10 самодельных смет
  разными почерками только ради специфики «работы+расценки»
  (помечать как синтетику); настоящие рукописные сметы добираем
  просьбой в чатах новосёлов. По бенчмаркам стабильных 95% на
  рукописных формах не даёт никто — вероятный исход: рукопись за
  честной деградацией; распечатки наших xlsx — единственная
  категория для git.

## Что показали замер и валидация

- По Excel (14 фикстур, настоящий `parse`): «нераспознанный
  хвост» — разделы, реквизиты и подписи без чисел (в 9 файлах из
  14 — ни одной потерянной позиции). Сценарий «LLM дораспознаёт
  хвост Excel» снят; Excel закрыт алгоритмикой (12/14), сметы без
  шапки — в «Дальше».
- По фото замера нет — это несущее допущение волны, поэтому F0
  идёт до любого прод-кода и даёт честную стоп-линию.

## Что уже есть (не делать повторно)

- `reqwest`, `sha2` в зависимостях; TLS из прод-образа работает.
  Vision — тот же `/chat/completions` с частями `image_url`
  (base64). Крейт `base64` уже в дереве зависимостей (через
  jsonwebtoken) — добавить прямое объявление, самописный энкодер
  хуже.
- `Secret`; образец опциональной интеграции `smtp_url:
  Option<Secret>`.
- Загрузка: multipart 10 МиБ, свой таймаут и rate limit; статусы
  uploaded/parsing/parsed/failed; UC-003.4 «переснимите» уже есть.
- Воркер: очередь в таблице, `SKIP LOCKED`, 3 попытки, подъём
  зависших через 10 минут — этот же stale-механизм станет
  естественным повтором для сбоев LLM (решение 8).
- Подтверждение почты уже реализовано (`auth/verify_email.rs`) —
  готовый барьер для дорогих входов.
- Часовой блок уборки в `jobs.rs`; `spawn_app_with` для настроек в
  тестах. HTTP-сервер в тестах не поднимался ни разу (всё
  `oneshot`) — фейковый провайдер это новая инфраструктура,
  отдельным тест-модулем (в `common.rs` не влезет: там 277 строк).
- В рабочем дереве не закоммичена волна ревью разбора
  (`estimates/parse/*`) — старт плана после её коммита.

## Решения (с причинами)

1. **Никакой абстракции «провайдер»**: OpenAI-compatible API — сам
   по себе интерфейс; смена = `LLM_BASE_URL`+`LLM_API_KEY`+
   `LLM_MODEL`. Провайдероспецифичные фичи в коде не используем;
   единственное исключение — данные (см. решение 2).
2. **Data policy исполняется настройкой аккаунта провайдера, не
   кодом**: провайдер-независимо запретить обучение нельзя. У
   OpenRouter — ZDR-маршрутизация и запрет data collection в
   настройках аккаунта (данные не хранятся и не идут в обучение —
   ровно это мы честно пишем пользователю); выбор
   модели — с подходящей политикой. Фиксируется в runbook; приёмка
   F1 включает «runbook описывает, как включить запрет и как
   проверять его при смене провайдера/модели».
3. **Без SDK-крейтов**; structured output не используем (не все
   провайдеры умеют): формат просим в промпте, разбираем строго у
   себя.
4. **Конфиг**: `LLM_BASE_URL` (по умолчанию OpenRouter),
   `LLM_API_KEY` (`Option<Secret>`, нет — выключено), `LLM_MODEL`.
   Прокинуть во все четыре места: `compose.prod.yaml` (переменные
   там поимённо!), оба `.env*.example`, `Settings::for_tests()`.
   Модель — из F0, не по памяти.
5. **Потолок один — глобальный, константой** `DAILY_TOKENS_CAP =
   2_000_000`/день (UTC-сутки; неатомарность принята: процесс
   один). Персональной токен-квоты НЕТ: её роль уже выполняют
   потолок 20 смет на аккаунт за всю жизнь (~сотни тысяч токенов
   максимум), барьер «фото — только с подтверждённой почтой»
   (решение 10) и глобальный потолок. Отдельная квота = код без
   угрозы, которую он снимает. Остаточный риск — ферма аккаунтов на
   одноразовых почтах, жгущая общий потолок, — принят осознанно до
   появления оплат (rate limit регистраций по IP уже есть);
   персональная квота вернётся вместе с платными разборами.
6. **Кэша НЕТ (в этой волне)** — важное отличие от ранней версии
   плана: у фото кэш-хитов почти не бывает (каждый кадр уникален
   байтами), а закэшированный брак убивал бы ретраи и повторную
   загрузку того же файла навсегда. Таблица `llm_calls` — только
   учёт: `prompt_tokens`, `completion_tokens`, `created_at` (без
   тел запросов/ответов — нечего чистить и нечему утекать; уборка
   старше 30 дней — одной строкой в часовом блоке). Кэш вернётся с
   потребителем, у которого повторные одинаковые запросы реальны.
   Формулировку предохранителя в product.md правим там же (F4).
7. **Ошибки различаются по одному признаку: виноват вход или нет.**
   Содержательный брак (модель ответила, но JSON негоден / числа не
   сошлись) — тратит попытку, после третьей — честный failed
   «переснимите» (UC-003.4). Транспорт/конфиг (таймаут, 5xx,
   401/403, выключенный LLM, исчерпанный потолок) — попытку НЕ
   тратит: смета остаётся в `parsing`, попытка возвращается
   (`attempts - 1`), stale-механизм повторит через 10 минут. Так
   исчерпанный бюджет означает «подождёт до завтра», а не мёртвую
   смету, занимающую слот из 20; неверный ключ не хоронит поток
   фото, а чинится оператором; и никакой лжи «файл нечитаем» из-за
   конфигурации. Верхняя граница обязательна: смета, не дошедшая до
   финального статуса за 24 часа, помечается failed со своим ключом
   («не получилось, попробуйте позже») — вечного `parsing` не
   бывает. Учёт при таймауте неполон (ответ не пришёл — токены не
   записаны) — принято: потолок страхует порядок величины, не
   бухгалтерию.
8. **Ретраев в клиенте нет** — повторяет stale-механизм воркера
   (решение 7), настоящими попытками с 10-минутным бэкоффом.
9. **`reqwest::Client` на вызов** (как oauth), таймаут 60 с
   константой. **Фото — не больше одного за тик**: тяжёлый вызов
   прекращает пачку, Excel-сметы не ждут пяти фото по минуте
   (признано следствие: Excel может подождать до ~минуты за одним
   фото — приемлемо).
10. **Фото — только с подтверждённой почтой.** Это и есть «дорогие
    входы — только вошедшим» из product.md, доведённое до дорогого
    входа: бесплатных аккаунтов без настоящей почты у vision нет.
    Механика подтверждения уже существует. Прод-пререквизит:
    работающий SMTP (без него почту не подтвердить и фото мертво
    для всех) — обязательной строкой в runbook.
11. **Разбор и почта — независимые циклы** `jobs.rs`: vision-вызовы
    не задерживают письма сброса пароля; заодно кривой `SMTP_FROM`
    перестаёт ронять разбор смет (сейчас общий `return`).
12. **Промпт против выдумывания**: «перепиши строки как видишь; не
    восстанавливай и не вычисляй числа, которых нет; неразборчивое
    верни отдельным списком как есть». Заголовки разделов («Стены»,
    «Потолок») переписываются тоже — структура сметы нужна будущей
    проверке «забытых работ»; фото-путь не должен терять то, что
    Excel-путь сохраняет. Где есть все три числа — сверка
    `quantity*price ≈ total` (допуск 1%), не сошлось — строка в
    нераспознанные. Фото — недоверенный вход: текст с него никогда
    не исполняется, только данные по схеме. Порог качества приёмки
    задаёт F0 числом.
13. **Бейдж «распознано ИИ» — свойство сметы, не строки**: смета с
    фото ИИ-шная целиком, признак уже есть в её типе файла. Колонка-
    флаг на строках (миграция, UNNEST, контракт) отклонена как код
    про будущее; появится с первой смешанной сметой.
13а. **Признак «смета с фото» — полем в контракте** (`Estimate`
    сейчас не отдаёт тип файла): добавляется в F3, где и так
    трогается `gen-api`; фронт не нюхает расширение из имени файла.
14. **Фронт не знает `llm::enabled`**: выключенный LLM — редкое
    операционное состояние; бэк отвечает на фото локализованной
    ошибкой, интерфейс не ветвится. Поле в контракте — когда
    состояние станет штатным (отклонено замечание валидатора,
    причина здесь).
15. **Vision-вызов — async вне `spawn_blocking`** (там живёт только
    calamine); фото-разбор — отдельным модулем `estimates/photo.rs`
    (в `worker.rs` и `parse/` не влезает по смыслу и размеру).
16. **Метрики**: `llm_calls_total{result}` ∈ `ok | capped |
    http_error | timeout`; `llm_tokens_total{kind}` ∈ `prompt |
    completion`; негодный JSON — метка в существующей метрике
    потребителя `estimates_parse_failed_total{reason}`, в одном
    стиле с её словарём (`no_data`, `too_big`, ...).

## Задачи

### F0. Замер качества vision на реальных фото (S) — гейт волны

**Планка задана здесь, до замера** (гейт, чью планку назначает сам
замер, — ритуал): на читаемом кадре ≥90% строк распознано, строк с
неверным числом ≤1%, выдуманных чисел — ноль (число там, где на
листе числа нет, — провал кандидата); сомнительная строка обязана
уходить в нераспознанные, это не штраф. На испорченном кадре брак
допустим, выдумка — нет.

Скрипт замера — `scripts/llm-probe.mjs` В РЕПОЗИТОРИИ (его же
переиспользуют приёмка F4 и runbook при смене модели), настоящий
ключ, корпус из раздела «Закрыто разведкой» (чужие распечатки —
основная сверка, скриншоты и рукопись — отдельные классы в
таблице). 5+ фото × 3–4 модели-кандидата
(фильтр data policy!), среди них обязательно минимум один
российский провайдер с OpenAI-совместимым API (Yandex AI Studio —
серверы в РФ, трансграничной передачи нет): таблица «строк верно /
чисел верно /
токенов и цена за фото / поведение на 10-МиБ кадре». Выход:
выбранная модель; `LLM_MODEL` для `.env.example`; `max_tokens`
(смета на 80 строк обязана влезать в ответ); пересчёт потолка в
«фото/день»; решение про размер фото. Вердикт — ОТДЕЛЬНО по
классам (печатное фото / скриншот / рукопись): волна вправе
стартовать с подмножеством — рукопись не прошла планку → фича
выходит для печатных, а слабо распознанная смета получает честную
подсказку «распозналось мало — лучше пришлите файлом» (F5), не
выдуманные числа. Стоп-линия: планку не прошёл ни один кандидат
ни на одном классе — волна останавливается, результаты в журнал,
план на пересмотр (preprocessing/другие модели/отказ).

### F1. `core/llm.rs`: клиент + учёт + потолок (M)

Миграция `llm_calls` (только учёт, решение 6); конфиг (решение 4);
`llm::enabled(settings)`; `llm::complete(pool, settings, request)
-> Result<String, LlmError>` — промпт + картинки (bytes+mime →
base64 `image_url`), `max_tokens` константой; потолок (решение 5);
ошибка различает «capped» от прочего (решение 7); метрики (решение
16); ключ только в `Authorization`. Фейковый провайдер — новый
тест-модуль (`tests/api/llm_stub.rs`): настоящий `TcpListener`,
заданный ответ, счётчик обращений. Runbook `docs/llm.md`: смена
провайдера/модели, data policy (решение 2), «сменил модель —
пересчитай потолок»; абзац в `architecture.md` (LLM в readiness не
входит; заодно поправить там ошибку — `jobs.rs` нарисован внутри
`core`); строка в `toolbox.md`.

Приёмка: тесты с фейком — успех пишет учёт и возвращает текст;
исчерпанный потолок — ошибка `capped` без сети; ключ не задан —
`enabled() == false`; секрет не светится в логах (образец теста
уже есть). `make verify` зелёный, журнал.

### F2. Развод циклов воркера (S)

`jobs.rs`: разбор смет и почта — две задачи tokio; уборка — в
почтовой. Обновить `architecture.md` («Письма и фоновые задачи») и
`toolbox.md` (строка про `spawn`). Приёмка: существующие тесты
зелёные; письмо уходит, пока разбор занят (без тайминг-зависимости
— медленный разбор стабится); кривой `SMTP_FROM` не останавливает
разбор. Журнал.

### F3. Приём фото на загрузке (M)

Формат живёт в пяти местах — правим все: миграция (CHECK по
`file_ext` в `0007`!), `ALLOWED_EXTS`/`extension_of`
(jpg/jpeg/png/webp), docstring OpenAPI → `make gen-api` →
contract-тест, `accept` на фронте (по MIME-типам
`image/jpeg,image/png,image/webp` — так iOS сам конвертирует HEIC
в JPEG при выборе из галереи), словари бэка
(`error-estimate-format`, тест `only_excel_is_accepted`) и фронта
(`estimates.hint`). Проверка сигнатуры файла (magic bytes, ~10
строк своих — jpg/png/webp различимы по первым байтам) на загрузке,
не «не позже разбора»: мусор не должен стоить трёх vision-вызовов.
Фото принимаются только при `llm::enabled` и подтверждённой почте
(решения 10, 14 — свои ключи ошибок). Поле «смета с фото» в
`Estimate` (решение 13а). Тест-хелпер подтверждения почты в
`common.rs` (письмо уже читается через `last_email_to`).
Фото-фикстуры из вопроса 3 —
с README-строками и ПДн-проверкой. Обновить UC-003 (статус,
сценарии, таблица «Приёмка → тесты», ограничение «один лист»).

Приёмка: тесты — фото проходит при включённом LLM и подтверждённой
почте; без подтверждения/при выключенном LLM — свои читаемые

Excel-путь не тронут. `make verify`, журнал.

### F4. Vision-разбор фото в воркере (M)

`estimates/photo.rs` (решение 15); ветка по расширению в `run_one`;
сигнатура воркера получает настройки (`run_pending(pool, files_dir,
settings)` через `Arc<Settings>` — планировщик сейчас копирует поля
поштучно, а `Settings` не `Clone`; правка `jobs.rs`, `bin/api.rs` и

строки сметы, неразборчивое — в нераспознанные (UC-003.5);
классификация ошибок и возврат попытки (решение 7); одно фото за

снятие «нераспознанного хвоста» как штатного применения LLM.

## Порядок и зависимости

Старт — после коммита незакоммиченной волны разбора; корпус
фикстур («Закрыто разведкой») собирается до F0. F0 — гейт: без его
таблицы не начинается F1. Дальше F1 → F2 → F3 → F4 → F5 → F6 (F2
можно параллельно F1). Пререквизиты ПРОДА, не старта кода:
работающий SMTP, опубликованная политика конфиденциальности со
строкой у формы, разовая консультация юриста по трансграничной
передаче/РКН.
