## 2026-07-26 — Инструмент проверки анимаций для агентов

**Что сделано.** Скрипт `web/scripts/motion.mjs` (`pnpm motion <url>
[селектор]`): открывает страницу в headless-браузере, при необходимости
кликает и печатает короткую сводку — какие анимации сработали (свойство,
длительность, easing), что изменилось в DOM, были ли дёрганые кадры,
какие сетевые запросы ушли. Плюс всего три кадра «до / в момент / после».
Прописан в toolbox и в скилле ux; в скилле writing-tests — правила, когда
его гонять и как строить качественный тест-кейс (одно действие на кейс,
сверка по числам из JSON, «резко» — не всегда баг, если осознанно).

Первый прогон по живым страницам (вход, смена темы, смена языка, пустая
форма, гостевой редирект): всё плавно, долгих кадров нет; кнопки
анимируют цвета за 150 мс, фон при смене темы меняется мгновенно
(осознанно допустимо); пустая форма входа гасится нативной валидацией
браузера без запроса в сеть. Замечание на будущее: на каждой гостевой
странице в консоли ошибка 401 от попытки обновить сессию — поведение
верное, но шумит в логах. Попутно починен сам инструмент: Playwright
прятал текстовый курсор перед кадром и мутировал style инпутов — отчёт
видел ложный DOM-шум (теперь `caret: 'initial'`).

**Зачем.** Нейронка проверяла дизайн по одиночным скриншотам — движение
на них не видно, а серия скриншотов съедает контекст. Числовая сводка
дешевле и точнее отвечает «плавно или резко».

**Как проверить.** `cd web && pnpm motion --self-test` — печатает сводку
с транзишеном opacity 300ms ease-out и завершается «self-test: ok».

## 2026-07-26 — Скилл design-check: агент проверяет дизайн по протоколу

**Что сделано.** Агент при ручной проверке дизайна часто говорил «всё ок»,

Вердикт «выглядит хорошо» без артефактов запрещён.

**Зачем.** Чтобы проблемы дизайна находились при проверке, а не после
явного «тут что-то мерцает» от человека.

**Как проверить.** Попросить агента «проверь дизайн страницы X» — он
должен пройти протокол и показать артефакты (кадры, числа, консоль), а не
ограничиться одним скриншотом.

## 2026-07-26 — Разбор аудита: чужие данные, обход второго фактора, CI мимо ветки

**Что сделано.** Закрыты находки внешней проверки кода.

1. *Чужие записи после смены пользователя.* Сайт помнил загруженные данные
   30 секунд, и следующий вошедший в той же вкладке успевал увидеть список
   предыдущего. Теперь при любом входе и выходе память данных очищается.
2. *Вход через VK/Яндекс обходил второй фактор.* Если у человека включено
   подтверждение кодом, вход через провайдера больше не пускает сразу:
   возвращает на страницу входа и просит код, как при обычном входе.
3. *Вход по чужой почте.* Раньше любой провайдер, назвавший адрес,
   попадал в аккаунт с таким же адресом. Теперь так можно только тем
   провайдерам, которые адрес проверяют (в настройках `TRUST_EMAIL=true`;
   у VK и Яндекса — да), остальным заводится отдельная учётная запись.
4. *Проверки на сервере сборки шли мимо главной ветки* — были настроены на
   ветку `main`, а главная у нас `master`; результат слияния никто не
   проверял. Плюс в проверки добавлен контроль размера файлов.
5. *Мелочи с крупными последствиями:* пароли считаются в отдельном потоке
   (раньше тяжёлый расчёт занимал поток, обслуживающий других
   посетителей); обновление сессии стало одной неделимой операцией
   (иначе «выйти на всех устройствах» могло не сработать); две
   одновременные регистрации на один адрес дают понятную ошибку, а не
   «внутреннюю ошибку»; приём ошибок фронтенда ограничен по частоте и
   размеру; счётчики ограничений и отправленные письма больше не копятся
   вечно; формы перестали отправляться дважды по двойному клику; вошедший
   не видит вспышку «войдите в систему» при перезагрузке; если сессию
   отозвали, интерфейс сам показывает выход вместо ошибок.

6. *Попутно починены браузерные тесты.* Шесть из одиннадцати не проходили
   и до этой работы (проверено на чистой главной ветке — это долг из
   записи «браузерные тесты дня не прогнаны локально»): схемы страниц
   отстали от разметки, два теста искали кнопку «Войти», которая теперь
   есть в двух местах, один открывал настройки, не войдя в систему, а
   настройка «уменьшить движение» до браузера не доезжала — теперь она
   включается явно, и все одиннадцать зелёные.

**Зачем.** Первые три пункта — прямые дыры в безопасности и приватности:
чужие данные на экране и обход второго фактора. Остальное — про то, чтобы
сервер не спотыкался под нагрузкой, а проверки ловили ошибки до продакшена.

**Как проверить.** `make verify` (нужен запущенный Docker) — зелёный
целиком: 45 тестов бэкенда, 24 фронта, 11 браузерных. Руками: войти одним
пользователем, выйти, войти другим — список записей перезагружается,
чужого не видно. Настройки провайдеров — docs/oauth.md.

## 2026-07-25 — Скриншоты трёх ширин экрана против эталонов (T5)

**Что сделано.** Три ключевые страницы (вход, главная, настройки)
фотографируются на ширине телефона, планшета и десктопа и сравниваются
с эталонными картинками. Сравнение живёт в отдельной проверке CI внутри
контейнера Playwright — только там пиксели воспроизводимы; на локальной
машине страницы просто прогоняются без сравнения (`make visual`).
Бэкенд для снимков не нужен: страницы получают одинаковые подставные
данные, поэтому картинки стабильны. Эталоны обновляются ручным запуском
той же проверки с галкой «update-visual»: она отдаёт новые картинки
файлом, их скачивают, смотрят глазами и коммитят. Эталонов в репозитории
пока нет — до первого такого запуска проверка вежливо пропускается.

**Зачем.** Это единственный слой, который ловит «кнопка уехала» и
«на телефоне всё наехало друг на друга»: схемы структуры геометрию не
видят. Мобильная поддержка объявлена обязательной в `docs/product.md`.

**Как проверить.** Запустить workflow ci вручную с галкой update-visual,
закоммитить артефакт в `web/e2e/__screenshots__` — следующие PR будут
сверяться; сломать вёрстку — джоб visual красный с картинкой-диффом.

## 2026-07-25 — Приложение уважает «уменьшить движение» (T6)

**Что сделано.** У людей, включивших в системе настройку доступности
«уменьшить движение», анимации приложения теперь выключаются целиком
(глобальное правило в стилях). Браузерные тесты эмулируют эту настройку
и бегут без анимаций — тест больше не может кликнуть по кнопке, которая
ещё «едет». Отдельный тест проверяет, что выключатель действительно
срабатывает, а не просто объявлен.

**Зачем.** Доступность (анимации мешают людям с укачиванием) плюс
стабильность тестов одним и тем же правилом в пять строк.

**Как проверить.** `make e2e` (нужен Docker) — тест «при „уменьшить
движение" анимации выключены»; руками — включить Reduce Motion в
системе и открыть приложение: переходы мгновенные.

## 2026-07-25 — Анимации не имеют права дёргать страницу (T3 плана UI-тестов)

**Что сделано.** Новый скрипт проверяет собранные стили: анимировать
можно только то, что не меняет раскладку (движение, прозрачность,
цвета). Анимация ширины, высоты или отступов — красный CI: именно такие
анимации заставляют браузер пересчитывать страницу каждый кадр, и
интерфейс «дёргается». Кнопка из библиотечного набора анимировала «всё
подряд» — теперь только цвета. Исключения возможны, но только файлом
со словесной причиной. Попутно починен хук проверки правок: он падал
на файлах, которые линтер осознанно игнорирует.

**Зачем.** Запрет причины дёрганья дешевле, чем измерение плавности:
он срабатывает детерминированно и до того, как анимацию увидят глаза.

**Как проверить.** `node scripts/check-animations.mjs` после
`pnpm build` в web — зелёный; добавить в любой css/компонент
`transition: width .3s` и пересобрать — красный.

## 2026-07-21 — Тесты фронтенда, красивый интерфейс, свежие версии, правила

**Что сделано.**
1. У фронтенда появились свои тесты: быстрые юнит-тесты (проверяют, что
   страница рисует список записей и форму) и сквозной тест — робот
   открывает настоящий браузер, создаёт запись и видит её в списке; при
   этом работает настоящая база данных.
2. Все тесты обложены таймаутами на каждом уровне (отдельный тест, весь
   прогон, сервер), поэтому «зависших в фоне и потерянных» тестов больше не
   будет: зависшее падает с ошибкой и убивается.
3. Интерфейс переведён на Tailwind CSS 4 и набор готовых компонентов
   shadcn/ui (поле ввода, кнопка, карточка) — современный стандарт.
4. База данных обновлена до PostgreSQL 18 — это последняя стабильная версия
   (19 существует только как «бета», в прод её брать рано). Учтена ловушка:
   в 18-й версии докер-образ хранит данные по новому пути.
5. Заведены правила для нейронок и людей: файл AGENTS.md (как писать код,
   тесты и этот журнал) и CLAUDE.md. Плюс «страховка»: после каждой правки
   файла автоматически запускается проверка типов, и ошибки чинятся сразу.

**Зачем.** Чтобы ошибки ловились сразу тестами, интерфейс выглядел
достойно, версии были актуальными, а ход работ был понятен без чтения кода.

**Как проверить.** В терминале: `make verify` — прогонит все проверки и
тесты (нужен запущенный Docker). Посмотреть сайт: `make dev`, затем
`cargo run --bin api` и `cd web && pnpm dev`, открыть http://localhost:5173.

## 2026-07-21 — Заложен монорепозиторий

**Что сделано.** Создан каркас проекта: бэкенд на Rust (веб-сервер и место
под телеграм-бота — оба используют одну и ту же «сердцевину» с логикой),
фронтенд на React, база PostgreSQL. Первая функция: список записей и
создание записи. Бэкенд-тесты гоняются на настоящей базе в докере,
контейнеры после тестов удаляются сами.

**Зачем.** Дешёвый сервер (весь бэкенд — один процесс на самом маленьком
VPS), быстрая разработка (ноутбук не делает тяжёлых сборок — они уехали в
CI), лёгкое подключение новых клиентов (бот зовёт те же функции, что и сайт).

**Как проверить.** `cargo test` — все тесты зелёные; `docker ps` после —
пусто.
