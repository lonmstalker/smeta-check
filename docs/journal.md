# Журнал проекта

Каждая задача — одна запись, новые сверху. Пишем простым русским языком,
чтобы было понятно без чтения кода.

## 2026-07-31 — T0: настоящие сметы для тестов и сертификаты в образе

**Что сделано.** В репозиторий добавлены 14 настоящих смет на ремонт из
открытых источников (`server/tests/fixtures/estimates/`): образцы
ремонтных компаний и вложения из форумного треда «оцените смету» —
8 файлов в новом формате Excel от пяти независимых источников и 6 в
старом от четырёх. У каждого файла записано, откуда он взят. Перед
добавлением все файлы просмотрены на персональные данные: телефоны,
адреса, ФИО и почта. Три файла с чужими данными не взяты вовсе, у
одного данные вычищены — что именно, написано в README рядом со
сметами. Отдельно починен прод-образ: в него доустанавливаются
корневые сертификаты, без которых приложение в контейнере не может
никуда сходить по https — вход через VK и Яндекс в проде был бы
сломан.

**Зачем.** Разбор смет надо проверять на живых файлах, а не на удобных
выдумках: в жизни шапка стоит не на первой строке, ячейки объединены,
а вместо цены пишут «от 600». Сертификаты — чтобы прод не встал на
первом же входе через соцсеть.

**Как проверить.** `ls server/tests/fixtures/estimates/` — 14 смет и
README с происхождением каждой; `docker build -t smeta-check .` и
`docker run --rm smeta-check ls /etc/ssl/certs | head` — список не
пустой.

**Зачем.** Чтобы первая большая стройка шла по проверенному плану, а
не по догадкам, и чтобы инфраструктура (файлы, фоновые задачи)

## 2026-07-30 — Правило: как добавлять новых клиентов API

**Что сделано.** В архитектурный документ добавлен раздел «Клиенты»:
вся логика живёт в доменных функциях, не зависящих от способа
подключения, поэтому новый клиент (мини-приложение Телеграма, мобильное
приложение, публичное API) — это отдельный тонкий «переходник», а не
правки внутри API для сайта. Отдельно зафиксировано, чего не делаем
заранее: версии `/v1`, отдельный сервис, ключи API — всё это появится
с первым настоящим внешним клиентом.

**Зачем.** Чтобы будущие клиенты добавлялись дёшево и не запутывали
основной код сайта.

**Как проверить.** Открыть `docs/architecture.md`, раздел «Клиенты:
как добавляются новые».

## 2026-07-30 — Харнес: напоминание перед сдачей и валидаторы планов

**Что сделано.** У нейронки-помощника появились два автоматических
напоминания: когда она собирается закончить работу, ей говорят, если код
менялся, а журнал — нет, и если после тестов остались забытые контейнеры
базы; а в начале каждой новой сессии ей показывают последнюю запись
журнала и живые планы, чтобы она сразу понимала, где остановились. Пять
«ракурсов» проверки плана из скилла `planning` оформлены готовыми
субагентами на модели opus (`.claude/agents/plan-*`) — промпты больше не
пишутся заново каждый раз. Мгновенная проверка размера файла после
каждой правки теперь покрывает и sql/css/словари/mjs, как основная.

**Зачем.** Правила «перед сдачей — журнал и make verify» и «план
проверяет свежая модель» держались только на памяти нейронки и к концу
длинной сессии забывались; теперь они срабатывают механически.

**Как проверить.** Поменять любой файл кода и попросить агента закончить —
придёт напоминание про журнал; `ls .claude/agents/` — пять файлов
`plan-*`; новая сессия начинается с блока «Ориентировка по проекту»;
`make check` зелёный.

## 2026-07-30 — Планы: волны, архив выполненных, runbook-доки

**Что сделано.** Уточнены правила процесса. Выполненный или остановленный
план теперь переезжает в `docs/archive/plans/` — в `docs/plans/` лежат
только живые (два июльских плана перенесены в архив). Большая работа
планируется «волнами»: детально — только ближайший этап до 400 строк,
дальнейшее — короткий список тем; следующий план пишется после
выполнения текущего. Проверяющему план запрещено читать архив и велено
сверяться с живыми планами. Справочники по настройке вроде
`docs/oauth.md` узаконены в списке документов как runbook.

**Зачем.** Выполненные планы (500+ строк) съедали внимание человека и
контекст нейронки при каждой сверке, а детальные планы далёкого будущего
устаревают раньше, чем до них доходят руки.

**Как проверить.** `ls docs/plans/` — только живые планы (сейчас пусто);
`ls docs/archive/plans/` — два июльских плана; правила — в скиллах
`workflow` и `planning`; `make check` зелёный.

## 2026-07-30 — Мутационные тесты: make mutants после готовой фичи

**Что сделано.** Цель `make mutants` (скрипт `scripts/mutants.sh`)
мутирует код диффа против master в обоих стеках и проверяет, замечают
ли тесты поломку; выжившие мутанты — готовый список тестов-пустышек.
Бэк — cargo-mutants, фронт — StrykerJS (`web/stryker.config.mjs`:
vitest-раннер, на мутанта гоняются только покрывающие его тесты,
строковые мутации в JSX отключены как шум, e2e не участвуют). Запуск —
только после полной реализации фичи (шаг дописан в финал скилла
new-feature), в цикле разработки не гонять: прогон долгий. Ноутбук не
перегревается: сборка уводится на энергоэффективные ядра
(`taskpolicy -c utility`), Stryker ограничен четырьмя воркерами, а без
поднятой dev-БД rust-часть не стартует — иначе каждый мутант поднимал
бы контейнеры. Полный прогон: `scripts/mutants.sh --all`; отчёты
(`mutants.out`, `web/reports`) — в `.gitignore`.

**Зачем.** Зелёный тест не значит честный: строка может исполняться,
но не проверяться — особенно в тестах, написанных агентами. Мутационный
прогон даёт машинный ответ, какие тесты ничего не ловят.

**Как проверить.** На ветке с изменениями `make mutants` печатает
пойманных и выживших мутантов; на чистом master — «нечего мутировать».

Первая находка: у `RequireAdmin` в `guards.tsx` выжили все мутанты —
гард оказался мёртвым кодом (ни одного админского маршрута нет) и
удалён по YAGNI; вернётся вместе с первой админской страницей и
тестом. После удаления mutation score файла — 100%.
