# smeta-check — правила для агентов

Детальные инструкции — в скиллах `.claude/skills/`: `workflow` (процесс и
документы), `planning` (составление и валидация планов), `new-feature`
(как делать фичу), `writing-tests` (тест-инфра), `ux` (стиль интерфейса),
`design-check` (ручная проверка дизайна живой страницы).
Здесь — короткие правила, действующие всегда.

## Процесс (кратко; детали — скилл workflow)

- Заметная фича начинается с use case в `docs/usecases/`, заканчивается
  записью в `docs/journal.md` на простом русском (дата, что, зачем, как
  проверить). Мелкая правка — только записью в журнал.
- Работа крупнее одной фичи (пачка связанных задач) начинается с плана
  `docs/plans/ГГГГ-ММ-<тема>.md` с блоком открытых вопросов; пока
  ключевые вопросы не закрыты — реализацию не начинать.
- Перед сдачей: `make verify` зелёный, `docker ps` без осиротевших
  контейнеров, в журнале — новая запись.

## Качественный код (определение)

Код качественный, когда:
1. его понимает человек, слабо знающий язык: простые конструкции, понятные
   имена, без хитрых дженериков/макросов/лайфтаймов без необходимости;
2. ошибки не глотаются: либо обрабатываются, либо осознанно пробрасываются;
   в HTTP-ответ уходит `ApiError` с ключом локализации, детали — в лог;
3. на новую логику есть тест в том же изменении;
4. границы соблюдены: домен не лезет в чужие таблицы, `core` не знает о
   доменах, HTTP-слой тонкий;
5. нет дублирования (см. ниже) и нет кода «на будущее» (YAGNI).

## Размер файлов — строго

- Цель — до 300 строк на файл; жёсткий потолок 400 (`make check` падает —
  скрипт `scripts/check-file-size.sh`). Проверяются код (rs/ts/tsx/mjs),
  миграции и стили (sql/css), словари (ftl) и документация (md). Большой
  файл съедает контекст человека и нейронки.
- Код дели по смыслу, а не механически: подмодули домена (пример:
  `auth/http/{session,recovery,totp,oauth_http}.rs`), отдельные страницы
  и компоненты на фронте, тест-файлы по сценариям
  (`auth.rs` / `auth_recovery.rs` / `auth_totp.rs`).
- Растущие доки не должны становиться бесконечным логом: у журнала при
  подходе к лимиту старейшие записи переноси в `docs/archive/journal-ГГГГ.md`
  (свежие остаются в `docs/journal.md`). Прочие доки дели по темам.
- Исключения — только генерённое (`schema.d.ts`), вендорное
  (`components/ui`) и `docs/archive/`; они уже прописаны в скрипте.

## Дублирование — строго

- Перед написанием функции/компонента/хелпера — открой индекс
  `docs/toolbox.md` (плюс `grep` по соседним доменам). Добавил новый общий
  хелпер — допиши его в индекс в том же изменении.
- Один и тот же код встретился дважды — при втором использовании выноси
  в общее место (core, lib, test-utils), а не копируй.
- Типы API на фронте НЕ пишутся руками — только из `src/api/schema.d.ts`
  (генерация `make gen-api`). Валидационные границы живут в OpenAPI-схеме
  и константах бэка; тест `contract` следит за совпадением.
- Тексты интерфейса и ошибок НЕ хардкодятся — только ключи локалей
  (бэк: `server/locales/*.ftl`, фронт: `web/src/locales/*.json`); на фронте
  за этим следит правило Biome `noJsxLiterals`.

## Меньше кода, но гореть продуктом

- Пиши только код, решающий текущую задачу. Каждая строка должна быть
  нужна сегодня, а не «пригодится потом».
- При этом оставляй код лучше, чем нашёл: увидел мёртвый код, кривое имя,
  дырку в тестах рядом с местом правки — поправь в том же изменении, если
  это дёшево; если дорого — запиши в `docs/backlog.md` (бизнес и техника
  раздельно, на входе фильтр честности — описан в самом файле).
- Эти два правила не противоречат: «меньше кода» — про новые абстракции,
  «улучшай» — про уже существующий код по пути. Спекулятивная гибкость —
  нет; уборка по ходу — да.

## Технологические правила

- Async-first: на бэке — tokio/axum (никаких блокирующих вызовов в
  хендлерах), на фронте данные — только через TanStack Query, никаких
  fetch в useEffect: UI не должен замирать.
- Локализация: любой текст пользователю — через словари; языки ru/en,
  ответы API — по Accept-Language. Тесты сверяют полноту словарей.
- Конфигурация: `std::env::var` живёт ТОЛЬКО в `core/config.rs`. Нужна новая
  настройка — поле в `Settings`, а не чтение окружения по месту.
- Логи: `tracing` с контекстом (request_id уже прикреплён middleware'ом);
  не `println!`. Секреты, пароли, токены в логи не попадают никогда.
  Фронт: `log` из `web/src/lib/logger.ts` — warn/error улетают на бэк.
- Метрики: доменные события считай через `metrics::counter!/histogram!`
  рядом с логикой; HTTP-метрики уже собираются автоматически.
- Версии зависимостей не бери «по памяти»: проверяй crates.io/npm.
  Беты и rc в прод не берём.
- Новая зависимость — только если её нельзя заменить парой строк.

## Подавления проверок — строго

- Проверку можно подавить только точечно и с причиной словами:
  `@ts-expect-error <почему>`, `#[expect(clippy::…, reason = "…")]`,
  `biome-ignore lint/…: <почему>`. Скрипт `scripts/check-suppressions.sh`
  ловит `@ts-ignore`, `.only` в тестах, `.skip` без объяснения,
  `#![allow(…)]` на весь crate и `env::var` мимо `core/config.rs`.
- `unwrap/expect/panic` вне тестов запрещены clippy: ошибку либо
  обрабатываем, либо пробрасываем (в тестах они разрешены).

## Тесты и ресурсы (кратко; детали — скилл writing-tests)

- Бюджеты: юнит-тест < 100 мс, интеграционный < 2 с, `make verify`
  локально < 5 мин, CI-джоб — в его timeout-minutes. Превысил — упрощай.
- Никаких watch-режимов в автоматике (`pnpm test` = `vitest run`).
- После прогонов не остаётся процессов и контейнеров.
- Тяжёлые (release) сборки — только CI/Docker; локально dev-инкрементал.
